# Viipio E1: user-selected candidate replacement undo

Status: contract only; **not implemented or tested**. This is distinct from Backspace undo of a swipe and the personal-word `+ Add → Undo` action. The active paths to change are `ManualCompletions.choose` and `EstonianSuggestionController.choose`, reached from the candidate buttons in `ViipioInputMethodService`.

## Behavior

A tap on a suggestion explicitly replaces only the word owned by that candidate offer. After a confirmed ET or EN replacement, show a short-lived **Undo** action in the existing fixed-height candidate row. Tapping it restores the exact original word once, without automatically changing anything else. Do not remove three candidate targets, insert another keyboard row, auto-correct, or persist the words. The original word is the *actual selected editor text before replacement*, not an inferred top-ranked dictionary entry when that differs. An unchanged candidate or unconfirmed replacement creates no undo action.

## Ownership and refusal

- At selection, retain a one-use, in-memory receipt bound to the current `EditorInfo` and `InputConnection` identities, input-view epoch, language, original text, replacement text, absolute replacement range/caret and bounded text on both sides. Never retain a receipt in private/incognito/no-personalization, secret, non-text or unidentifiable fields. Do not log the words.
- A manual completion can span a word at an interior caret; use its already verified whole-word range, and capture the successfully replaced range from editor readback. A swipe candidate uses its own confirmed owned word and absolute selection, not a suffix spelling match alone. Refuse creation when selection or final editor state cannot be proven. `ExtractedText.startOffset` participates in absolute coordinates.
- Before Undo, require the same field, connection, view epoch and language; a collapsed caret exactly at the replacement end; no selected text; exact replacement range, bounded left/right context and a trustworthy left boundary (a truncated returned suffix is not proof); no active composition that could cause `commitText` to replace a different range. Revalidate after finishing any owned composition. Decline on null/exception/short ambiguous readback.
- Select only that verified replacement range, confirm `getSelectedText()` byte-for-byte equals the replacement, then perform one `commitText(original, 1)`. On refused `setSelection`, selection mismatch, refused commit, or uncertain post-write state, invalidate the offer and do not retry a potentially applied write. If a refused commit merely leaves the range selected, restore the caret only when the same editor and selection are still provable. Do not delete the replacement first.
- Invalidate on external selection/editor text changes, next typing/swipe, language or view switch, field exit, privacy transition, teardown and expiry. Own selection callbacks from the replacement must not immediately invalidate its receipt; a later external callback must. A rejected attempt must not write another field's text. The existing `+ Add → Undo` stays independent and retryable for its own durable-store path.

## RED → GREEN validation

Start with one real controlled `InputConnection` test for a manual ET candidate: selected replacement yields a visible/actionable receipt and Undo restores the original while preserving surrounding text. Verify the test fails for the absent behavior before implementation. Extend one behavior at a time to EN and swipe candidates, interior caret and duplicate words, stale field/connection/view/language, changed context at the same caret, selected text, unreadable or truncated context, secret fields, rejected selection/commit, and single-use expiry. Test the active candidate-button → controller → editor path, not merely a policy class. Then run guarded targeted and full tests, review the diff, and check an installed signed ARM64 APK in ET/EN and a sensitive field with the shared emulator restored afterward. **No release while SDK/ADB or any gate is unavailable.**
