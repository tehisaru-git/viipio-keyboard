# Viipio language modes — proposed product policy

**Status: design decision for a future release, not implemented in v0.8.0.** The current APK includes ET and EN, starts its active keyboard in ET and allows a two-way toolbar switch. A language mode is a selection inside the **one installed** `io.github.tehisaru.viipio` app, not another installed app or package ID. Later, distinct APK **distribution variants** may preinstall different languages while retaining that App ID and signer; they are alternative offline-ready installers, not simultaneously installed keyboards. The [staged language-distribution plan](../plans/viipio-language-distribution.md) defines this future path. This policy replaces the assumption that every user must see both keyboards; it does not remove either language from the product.

## User-facing choices

- **English only:** EN QWERTY, EN swipe and EN suggestions/personal words. No ET key layout or ET/EN toggle in the typing surface. ET data is not consulted for EN candidates. The installed APK may still contain ET assets until an optional-pack design proves worthwhile.
- **Estonian + English:** ET keys and ET dictionary when ET is active; EN keys and EN dictionary when EN is active. Show a clear, accessible switch and indicate the selected language. No automatic mixing of the two lexicons or silent language switching. Preserve a user-selected active language across ordinary app/editor transitions where safe; switch revokes in-flight predictions and suggestions.
- **Estonian only (optional):** the same isolation and hidden toggle as English only, with ET as active language. Keep this option if it is inexpensive to test and maintain; do not force an Estonian user to enable EN.

On a fresh install, **ask the user to choose** among the supported modes during setup. The system locale may inform an *unconfirmed suggestion*, not silently enable or remove a language. An older v0.7/v0.8 installation has no saved enabled-language set or durable active-language selection: migrate that **absence** to ET+EN and initial ET, exactly the existing startup/switch behavior; do not claim to recover which language happened to be visible before the app restarted. Once a new mode/active choice is actually saved, retain both across ordinary app/editor transitions where safe. If the user selects English only while ET is active, atomically cancel old predictions, set the enabled set to `{EN}` and active language to EN; for Estonian only, use `{ET}` and ET. For ET+EN retain an already enabled active language, otherwise choose ET on first migration. A malformed saved state must fall back without losing personal words or changing diagnostic consents. An upgrade must not change Android's selected IME, preferences or stored words; the older active ET/EN selection was never durable. A v0.6-or-earlier installation has a different package ID and is **not** a migration path. Keep diagnostics opt-in and OFF unless the existing user consent already says otherwise; mode changes do not create diagnostic consent or delete/export private words.

## Implementation boundaries and acceptance

1. Define one persisted enabled-language set and one active language. Validate that the active language belongs to the enabled set; if a saved value is invalid, fall back safely without writing to a different language's store. Show mode choices in the active Settings route and the first-run flow, not an inherited CleverKeys panel. Never claim that the mode exists merely because the old two-way toolbar switch works.
2. Pass the selected language consistently through key geometry, touch/accessibility, manual completions, CTC/geometric lookup, priority and personal-word overlays. On language/mode change cancel stale asynchronous results. A disabled language has no suggestion or visible toggle, and its word store remains intact for later re-enabling. Numeric/PIN fields keep their special safe layouts and no learning regardless of mode.
3. Test fresh EN-only, ET+EN and optional ET-only; ET→EN→ET transitions; a mode change while decoding; personal words and privacy isolation; editor switches, restarts and upgrades from an existing ET+EN install. In an installed APK verify the drawn keys, accessible switch, actual word committed in both modes and sensitive-field exclusions. Preserve the same signer/App ID and do not mutate historical APKs.
4. Measure cold/warm start, memory, APK size and actual user tasks **before** claiming that EN-only becomes faster or smaller. Removing bundled ET assets or introducing downloadable packs would need separate offline/reproducibility, licence, failure and update tests; it is not a prerequisite for hiding an unwanted ET keyboard.

Quality priorities stay ET/EN everyday typing, correction and privacy. English-only users should not have ET in their typing interface; ET+EN users should retain explicit, reliable access to both. This is a product hypothesis to validate with users, not a measured claim about how many English-speaking people want Estonian.
