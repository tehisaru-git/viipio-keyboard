# Viipio development checks: faster feedback without weaker release gates

## Observed bottlenecks and evidence

- A Kotlin production/test change made a focused guarded Gradle run take **6m 48s** on this host; a cached rerun of a small selection took **30s**. Filtering with `--tests` does **not** avoid compiling the production and test sources first. Repeating a build after every tiny edit is therefore expensive; the useful unit of compilation is one coherent, frozen change set.
- At inspection, the host had **4 CPUs**, **15 GiB RAM**, **5.0 GiB MemAvailable** and **8.8/9.0 GiB swap already used**. This does not prove current thrashing, but it makes concurrent Gradle workers and another emulator a poor bet. The shared emulator has a roughly 2.8 GiB resident process. Do not kill unrelated services to reclaim memory.
- `scripts/gradle-guard.sh` already provides a device-wide singleton, one worker, no accumulating Gradle daemons, bounded heap and a low-memory abort. Keep it as the *only* Gradle entry point; never bypass it to make a benchmark look faster.
- A filtered Gradle run can leave only its selected XML suite results. `BUILD SUCCESSFUL` alone does not prove that the full suite ran. Earlier inherited full-suite attempts could run into an OutOfMemoryError cascade; don't label those a pass or silently replace them with focused checks.
- Existing UI, decoder and telemetry interact across editor ownership and consent boundaries. Parallel edits to the same IME service or diagnostics store make test results ambiguous. Parallelize *read-only* reviews or independent modules, then serialize integration and builds.

## Implemented workflow

Run `python3 scripts/viipio-check.py quick` after each small edit: unstaged **and staged** `git diff --check` plus the Viipio Python guards. Git cannot check untracked new files: review them separately, then stage them and repeat `quick` before committing. This check makes no Gradle invocation and does not assert Android runtime behavior.

Once a coherent production/test slice is frozen, run `python3 scripts/viipio-check.py targeted` with `ANDROID_HOME` and `ANDROID_SDK_ROOT` set to the actual SDK. It invokes the guarded Gradle wrapper once with the active service, release-metadata, personal-word, CTC lexicon merge, typed-word, correction, manual-completion, telemetry and swipe-study test classes. It parses JUnit XML and fails if an expected class has no executed tests, a report predates the invocation, or failures/errors are present. Add a new project-specific test class to the `TARGETED` tuple in the script when introducing one. **Do not edit Kotlin sources until that run completes.** If a compile or assertion fails, fix it and rerun only the relevant small classes before repeating the whole targeted set. An `UP-TO-DATE` Gradle result with old XML is not evidence that these tests ran again; use `python3 scripts/viipio-check.py targeted --rerun` for an explicit guarded fresh run (this expensive fallback reruns other Gradle tasks too).

At a candidate release snapshot, run `python3 scripts/viipio-check.py full`. This runs the full `testDebugUnitTest` task with an *opt-in* `forkEvery=40` and one parallel test fork, renewing the test JVM periodically instead of letting one long-lived worker accumulate model/trie memory. This is a memory-reliability measure, **not a proven speed gain**, and does not alter ordinary CI. Record the full XML suite/test/failure totals; investigate and retain failures rather than filtering them away. If a class itself exhausts memory, reduce the batch size only after inspecting that failure, not by raising host-wide concurrency.

Then build the normal release graph, inspect the actual signed APK's ABI, package, version, signing identity and merged permissions; install the newly built APK in a bounded session on the shared emulator and check real editor readback, consent/export/erase and UI. Record the initial IME and foreground app once; batch ET/EN, Space, first-use help, Settings and sensitive-field probes while Viipio remains selected. The owner does **not** require restoring Gboard between these subprobes. Clean synthetic words and test editors, then restore the initial IME/foreground once at completion, failure or shared-emulator handoff. **Separate an explicitly experimental, owner-testable distribution from a production-ready release.** For an experimental APK, independently classify every red full-suite assertion, reject any active-IME or privacy regression, pass the scoped security/editor tests and installed smoke checks, and disclose the exact red total and untested Pixel behavior prominently; never call its full suite green. Do not require the owner's Pixel 8 feedback *before* giving them an installable experimental build—their test follows distribution. A production-quality claim still requires the full regression and physical-device gates or an explicit, evidence-backed disposition of inherited failures.

## Practical sequencing

1. Write a failing focused regression for one behavior; implement only that slice; use `quick` for format/route checks, then a single focused guarded Gradle run once the snapshot is stable.
2. Integrate other nonconflicting modules and freeze; run `targeted` once. Do not launch a second Gradle job or mutate Kotlin files during it.
3. Ask for read-only review of privacy/provenance, service connections and release metadata in parallel; fix confirmed findings, rerun relevant tests, then `full` on the final snapshot.
4. Build/install/inspect on emulator only after the source and test snapshot passes. Do not use the old installed APK as evidence about new code.
5. Save timing and XML counts in the release verification note; use them to decide whether narrower test source sets or a dedicated CI machine would actually improve feedback. Changing production architecture merely to speed tests needs its own correctness case.

## Operating procedure after v0.8.0 (activate per project need; inspect the live job state)

**Goal:** deliver one small, useful, installable behavior slice at a time while preserving the offline/privacy and source-to-APK gates. The [language-mode policy](../specs/viipio-language-modes.md) is a future design contract, not a v0.8.0 feature. Historical steps below explain prior failures; do not reclassify an old release because a later branch is green.

1. **Intake and choose one slice.** Keep a short ordered backlog: owner-identified blockers first, then reproducible ET/EN input/correction/privacy defects, then documented and observed Gboard core behavior. For each entry record its evidence tier (owner report, opt-in aggregate log, Google documentation, controlled black-box test or code hypothesis), affected language/editor, falsifiable acceptance test, privacy/licence implications and remaining physical-device gap. Never call an unmeasured feature popular or imply proprietary Gboard code is redistributable. Freeze one primary integration slice; new independent ideas queue for the next release rather than expanding a release indefinitely.
2. **Parallelize only safe work.** Give independent agents nonoverlapping research, fixtures/tests, licensed-source checks or read-only review; integrate only after reading their actual diff and results. One owner controls the active IME service, shared Gradle guard and emulator. No two agents compile against a changing Kotlin tree, sign APKs or change emulator IME concurrently. Do not start a second emulator to compensate for a slow build. Use a separate worktree for any disjoint code writer; merge only after source ownership is clear.
3. **Fast-to-slow checks.** Start with a failing behavior regression; after each coherent edit run `python3 scripts/viipio-check.py quick` (both unstaged and staged whitespace plus Viipio Python tests). Freeze Kotlin sources, then run `targeted` once for related service/gesture/privacy suites **including release metadata, personal words and CTC lexicon merge**; confirm all requested suite names and counts in XML. The release-metadata test must run **before the broad suite** immediately after the version and candidate note are both edited: `bash scripts/gradle-guard.sh testDebugUnitTest --offline --tests 'tribixbite.cleverkeys.ReleaseMetadataDriftTest'` (with the real `ANDROID_HOME`/`ANDROID_SDK_ROOT`). `quick` is Python-only and does **not** run that JVM check. Fix any focused failure and repeat the affected suite before another targeted run. A documentation-only edit does not need a speculative full Android rebuild, but still needs link/claim review and quick checks.
4. **Candidate gate.** On the final frozen source, run `full` via the guarded single-worker Gradle path and reconcile JUnit XML counts, errors and skips. Independently review input ownership, sensitive-editor exclusions, persistence, dependency/data licences and release copy. Build a real signed ARM64 APK; compare shipped assets, package ID, versionCode, signer, permissions and ABI; install it on the shared emulator, verify editor readback, language-mode isolation when that feature exists, PIN/diagnostics and upgrade semantics; batch those probes and restore the prior IME/Home once at completion or handoff. The owner's Pixel 8 finger tasks remain separately labelled untested until supplied. A new permission, paid service, signer/package migration or non-redistributable data needs an explicit owner decision, not a silent autonomous shortcut.
5. **Conditional cadence, not calendar-driven publishing.** A reasonable target is weekly experimental candidate review and release **only when** the gate passes and the signed asset offers a meaningful tested improvement. If blocked, report the exact failed assertion or missing evidence in this thread and continue with a different safe, independent backlog slice; never rewrite a published tag/APK or mint an empty version to meet the clock. Before any unattended signing/publication, confirm a secure off-host backup of the Viipio signing key/password and an owner-approved automation scope. On a valid release read back the exact public tag, draft/prerelease state, asset count, anonymous APK checksum and source identity; preserve the last known working APK.
6. **Durable orchestration after approval.** Use one bounded, self-contained scheduled run anchored in this repo and this thread, with explicit working-tree/build-lock preflight, one verifiable slice per run and a concise result or blocker. A child agent or active conversation is not durable automation. The interactive thread handles an owner's stop/change-of-direction by canceling or pausing the scheduled job; a cron session must not require a Discord reading connector that it does not have. If a scheduled worker cannot access the actual SDK or ADB, report that once and pause or hand off the emulator step to a verified-access session instead of repeatedly spending runs on the same unavailable probe. Avoid duplicate project jobs or overlapping source/Gradle/emulator runs. Do not create a development cron job merely because this procedure describes one; scheduling and regular unattended publishing remain separate activation decisions.

**Why this is faster without a weaker gate:** a measured fresh focused build took 6m48s versus a cached rerun's 30s; filtered Gradle still compiles the source. Batch coherent changes instead of recompiling each micro-edit. The v0.7.0 tag's 5,591-test/41-failure broad run and later green `main` are different snapshots; catch that debt before claiming a later candidate green. The v0.8.0 source had 5,601 tests, 0 failures and 13 skips, plus four bounded instrumented tests; skipped tests and human-finger accuracy do not become passes through faster orchestration. Record actual time and failure distribution on the next slice before claiming any new speedup.

## Full-suite failure triage: legacy editor path (historical v0.6.0, 15 November)

The `EstonianSwipeService` mentions below describe the original v0.6.0 source snapshot; the active service class was renamed `ViipioInputMethodService` in v0.7.0. The recorded failure IDs remain comparable but this paragraph is not a new installed-APK check.

The XML reports for `BlindFieldPolicyTest` (1 failure), `SwipeAutocapCommitTest` (6) and `TypedBarHighlightHandlerTest` (4) were compared against the separate v0.5.1 baseline worktree's XML, not just their test IDs. Their assertion messages match in substance: ordinary-editor correction removes the replacement (`ok hello` → `ok `), six mocked swipe commits supply `null` instead of the expected word, and four space-correction tests leave the mock editor empty. These 11 assertions exercise `SuggestionHandler` fixtures; the source manifest selects `EstonianSwipeService`, whose source does not call `SuggestionHandler`. This narrows the v0.6.0 regression investigation, but does **not** waive the 11 failures or prove that the active service's corresponding editor actions work. The other 30 assertions were also compared one by one against the v0.5.1 baseline XML, including their failure messages: all 30 match in substance. They comprise `TestKeyboardSectionTest` (1: inactive settings panel absent), `LearningFunnelBookkeepingTest` (3: editor/auto-insert expectation), `SettingsSurfaceDriftTest` (2: `has_visited_calibration` reader/writer classification), `DebugLoggingManagerTest` (1: test path `/tmp/dlm-test/swipe_log.txt` versus `/data/`), `SwipeCorrectionOfferTest` (14: inherited `SuggestionHandler` editor/offer fixtures), and `WindowLayoutUtilsTest` (9: expected exception not thrown by mocked window). Neither the test files nor the active `EstonianSwipeService` references show these assertions exercising the active service; in particular the service has no `SuggestionHandler` or `WindowLayoutUtils` reference. Matching baseline failures narrow regression triage, **not** a waiver or a proof of active IME behavior. The complete 41-failure full gate stays red. Next verify the active correction/undo and consent boundaries in a controlled installed editor, then decide whether to repair inherited tests or document an explicit, independently reviewed release gate; do not mark the full suite green.
