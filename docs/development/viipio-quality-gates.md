# Viipio development checks: faster feedback without weaker release gates

## Observed bottlenecks and evidence

- A Kotlin production/test change made a focused guarded Gradle run take **6m 48s** on this host; a cached rerun of a small selection took **30s**. Filtering with `--tests` does **not** avoid compiling the production and test sources first. Repeating a build after every tiny edit is therefore expensive; the useful unit of compilation is one coherent, frozen change set.
- At inspection, the host had **4 CPUs**, **15 GiB RAM**, **5.0 GiB MemAvailable** and **8.8/9.0 GiB swap already used**. This does not prove current thrashing, but it makes concurrent Gradle workers and another emulator a poor bet. The shared emulator has a roughly 2.8 GiB resident process. Do not kill unrelated services to reclaim memory.
- `scripts/gradle-guard.sh` already provides a device-wide singleton, one worker, no accumulating Gradle daemons, bounded heap and a low-memory abort. Keep it as the *only* Gradle entry point; never bypass it to make a benchmark look faster.
- A filtered Gradle run can leave only its selected XML suite results. `BUILD SUCCESSFUL` alone does not prove that the full suite ran. Earlier inherited full-suite attempts could run into an OutOfMemoryError cascade; don't label those a pass or silently replace them with focused checks.
- Existing UI, decoder and telemetry interact across editor ownership and consent boundaries. Parallel edits to the same IME service or diagnostics store make test results ambiguous. Parallelize *read-only* reviews or independent modules, then serialize integration and builds.

## Implemented workflow

Run `python3 scripts/viipio-check.py quick` after each small edit: `git diff --check` and the Viipio Python guards. This check makes no Gradle invocation and does not assert Android runtime behavior.

Once a coherent production/test slice is frozen, run `python3 scripts/viipio-check.py targeted` with `ANDROID_HOME` and `ANDROID_SDK_ROOT` set to the actual SDK. It invokes the guarded Gradle wrapper once with the active service, typed-word, correction, manual-completion, telemetry and swipe-study test classes. It parses JUnit XML and fails if an expected class did not actually run or if failures/errors are present. Add a new project-specific test class to the `TARGETED` tuple in the script when introducing one. **Do not edit Kotlin sources until that run completes.** If a compile or assertion fails, fix it and rerun only the relevant small classes before repeating the whole targeted set.

At a candidate release snapshot, run `python3 scripts/viipio-check.py full`. This runs the full `testDebugUnitTest` task with an *opt-in* `forkEvery=40` and one parallel test fork, renewing the test JVM periodically instead of letting one long-lived worker accumulate model/trie memory. This is a memory-reliability measure, **not a proven speed gain**, and does not alter ordinary CI. Record the full XML suite/test/failure totals; investigate and retain failures rather than filtering them away. If a class itself exhausts memory, reduce the batch size only after inspecting that failure, not by raising host-wide concurrency.

Then build the normal release graph, inspect the actual signed APK's ABI, package, version, signing identity and merged permissions; install the newly built APK in a bounded session on the shared emulator and check real editor readback, consent/export/erase and UI. Record and restore the original IME and foreground app in `finally`. **Separate an explicitly experimental, owner-testable distribution from a production-ready release.** For an experimental APK, independently classify every red full-suite assertion, reject any active-IME or privacy regression, pass the scoped security/editor tests and installed smoke checks, and disclose the exact red total and untested Pixel behavior prominently; never call its full suite green. Do not require the owner's Pixel 8 feedback *before* giving them an installable experimental build—their test follows distribution. A production-quality claim still requires the full regression and physical-device gates or an explicit, evidence-backed disposition of inherited failures.

## Practical sequencing

1. Write a failing focused regression for one behavior; implement only that slice; use `quick` for format/route checks, then a single focused guarded Gradle run once the snapshot is stable.
2. Integrate other nonconflicting modules and freeze; run `targeted` once. Do not launch a second Gradle job or mutate Kotlin files during it.
3. Ask for read-only review of privacy/provenance, service connections and release metadata in parallel; fix confirmed findings, rerun relevant tests, then `full` on the final snapshot.
4. Build/install/inspect on emulator only after the source and test snapshot passes. Do not use the old installed APK as evidence about new code.
5. Save timing and XML counts in the release verification note; use them to decide whether narrower test source sets or a dedicated CI machine would actually improve feedback. Changing production architecture merely to speed tests needs its own correctness case.

## Limits

The latest `quick` run passed **32 Viipio Python tests**; the explicit ARM64 JUnitCore registry includes 30 previously unregistered Viipio classes and its drift suite passed **2/2** after a fail-first **1/2** run. Registration has not been exercised by the separate `runMockTests` runner and is not a full-suite pass. After numeric/PIN and active Undo/caret fixes, `targeted` passed **151 tests across all 13 expected XML suites**. The final broad run completed in **11m58s: 5,591 tests, 41 failures, 0 errors, 13 skipped across 530 XML suites**. All 41 failing class/test identifiers exactly matched the preceding 5,590-test run; the original 44 identifiers were also red on a **158-test, 12-class v0.5.1 baseline run**. Individual failure messages for the 41 were compared against baseline separately, but this does not imply a passing full suite or universally safe behavior. A separately installed ARM64 synthetic probe confirmed Backspace and glide-delete Undo → manual correction JSONL linkage, Stop/Erase across restart and PIN non-collection, with Gboard restored. The clean-checkout Compose inputs fixed in commit `8345775` and eight additional JSON packaged inputs are now tracked; the APK's eight JSON assets match the latter's source bytes. `forkEvery` has not been shown to improve speed. The explicitly experimental owner test release discloses the red inherited suite and outstanding Pixel 8 human-finger validation; it does not waive privacy, independent review or active-path gates.
