# Viipio language distribution — staged plan

**Status: plan, not a v0.8.0 feature or permission change.** This records the owner's preference: ordinary users should be able to choose, download, update and remove languages **inside Viipio**; they should not have to find a ZIP in a browser and import it with a file picker. Later, offer distinct APKs with useful languages preinstalled so a fresh installation can type offline without downloading anything. For now develop and release **one** signed ET+EN APK, keeping the existing one-asset install/update path understandable. The [language-mode policy](../specs/viipio-language-modes.md) governs visible EN-only, ET+EN and optional ET-only behavior independently of how resources are delivered.

## Stage 0 — current release, unchanged

v0.8.0 bundles ET and EN dictionaries and layouts in one APK, starts in ET and switches manually to EN. It has **no INTERNET permission**. The inherited ZIP import control in Settings is a technical starting point, not a satisfactory ordinary-user download flow or proof that all language-dependent resources can be moved out of the APK. Neither additional APK flavors nor in-app downloads have been implemented. Keep the published APK, tag, package ID and signing certificate unchanged.

## Stage 1 — one APK, built-in language management

1. Keep a usable ET+EN offline baseline while adding the selected-language modes. Settings and initial setup should list installed and available languages, required space, source/licence and version; offer **Download**, progress/cancel, install, update, retry and remove in Viipio. A downloaded pack can be removed; a language preinstalled inside the APK can be disabled/hidden, but removing it from Settings cannot reclaim the APK's embedded bytes. An EN-only user need not see an ET keyboard; an ET+EN user can select both without leaving the app. Offer a short, intelligible offline/retry state instead of silently failing or blocking the keyboard.
2. A future **user-initiated** in-app fetch needs a reviewed Android `INTERNET` permission and a pinned, HTTPS-based catalog or equivalent authenticated release metadata. No permission is added by this plan. Downloaded pack bytes and metadata must be authenticated by an app-trusted publisher signature or an APK-pinned digest; a hash supplied only inside the same untrusted ZIP is an integrity check, not proof of publisher identity. Verify size limits, ZIP paths, format, language code, schema, source licence, APK/pack compatibility and usable CTC/geometric/manual-suggestion paths before activation. Treat pack data as untrusted; never execute pack-supplied code. Use temporary storage and an atomic swap with rollback so an interruption or invalid update leaves the last working language intact. Avoid downloads while typing and unnecessary background network use; any later automatic pack update is a separate opt-in design.
3. A language pack may carry its dictionary and frequency/ranking data, spelling/contraction rules, layout and diacritic metadata, emoji/search aliases and attribution as needed. The decoder and privacy/editor-ownership rules stay in the app. Do not assume the existing ZIP importer already activates every such field: the current ET layout is tied to the active keyboard code, and ET CKDT and EN JSON have different CTC scoring scales. A changed EN source needs a held-out ranking regression test, not merely a successful file import. Personal words, swipe priorities and diagnostic records stay private and language-scoped in app storage, not in a public pack or its catalog. A missing optional pack must not leak another language's suggestions or destroy a saved user's words.
4. Test fresh/offline/restart/low-storage/partial-download/corrupt-signature/rollback/older-pack/newer-APK/removed-active-language cases. Check sensitive fields and no-network typing, ET/EN editor readback, language isolation and existing users' data on a signed installed APK. Measure startup, memory, battery and user task completion before claiming smaller/faster typing. The present manually imported-pack path may remain for advanced/offline transfer, but must not be the only user-facing installation path once Stage 1 is announced.

## Stage 2 — distinct offline-ready APK variants, after Stage 1 works

- Build from **one codebase** at least an **English-preinstalled** and an **Estonian+English-preinstalled** signed APK; consider ET-only only if demand and test costs justify it. Each is usable without internet on first launch. The in-app manager can still add/remove optional languages later. Do not ship a completely language-empty bootstrap that cannot type when offline.
- Prefer the **same `io.github.tehisaru.viipio` App ID and Viipio release signer** for these mutually exclusive install choices, so an existing installation's app data need not be migrated merely to choose a bundle. They **cannot coexist** under the same Android user. Distinct package IDs would allow coexistence but would make them separate Android apps with separate private words/settings and incompatible in-place updates; choose that only after a new owner-approved migration decision.
- Plan Android versionCodes and release assets together. A switch from a higher-code variant to a lower-code APK at the same version is a downgrade, even with the same signature; do not promise arbitrary cross-variant APK switching. Keep mode/pack switching **inside the app**, and make every next release's codes higher than all codes in the prior release. Verify in-place updates **for each variant**, the unchanged signer, correct App ID/ABI and exact installed preloaded contents. Give each APK a distinct asset name and explicit channel/asset-selection instructions (including Obtainium behavior); the present single-asset release cannot simply acquire several APKs without checking how clients choose one. Record checksums and keep old tagged assets immutable.
- Compare the final APK sizes and cold/warm latency before claiming that a variant saves space or time: raw dictionary-file sizes alone do not establish compressed APK or runtime gains. Ensure an EN-only build never loads ET resources by default, while the ET+EN build remains a complete offline keyboard. Keep source/licence notices with every variant and separately downloaded pack.

## Release/activation boundary

Do not start Stage 1 or create additional APKs, an update service, a catalog, network permissions or new release assets merely by writing this plan. Implement in bounded test-first slices through the [guarded development process](../development/viipio-quality-gates.md); maintain the existing v0.7→v0.8 update path. Any permission, hosting, distribution-channel or signer change receives an explicit scope/security review before publication. Publish only a tested, signed artifact with the actual offline/update behavior described truthfully; keep another keyboard available during experiments.
